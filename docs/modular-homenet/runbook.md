# HomeNet Core 1.0.0 + DMS 0.4.0

NPM-63 / DMS-3. Этот документ описывает подготовленный способ установки.
Команды для роутера выполняются только после отдельного разрешения на выкладку.
Локальная сборка и фикстуры не подтверждают работу на конкретном устройстве.

## Состав и сборка

Core содержит оболочку, Account/ACL, портал, реестр, шлюз и координатор операций.
Proxy, Network и VPN — отдельные worker binaries и ES-пакеты с manifest API/UI 1.
DMS — отдельная базовая служба; через UI нельзя удалить Core, DMS или Account.
Каждая изменённая поставка получает новую версию. Повторная загрузка того же
номера с другим содержимым отклоняется.

Из корня NPM на машине разработки:

```powershell
node scripts/build-modules.mjs amd64 1.0.0
# Последующие архитектуры используют уже собранные UI:
node scripts/build-modules.mjs arm64 1.0.0 --reuse-ui
node scripts/build-modules.mjs arm 1.0.0 --reuse-ui
node scripts/build-modules.mjs mips 1.0.0 --reuse-ui
node scripts/build-modules.mjs mipsle 1.0.0 --reuse-ui
node scripts/pack-modules.mjs arm64 /absolute/path/dms-client.exe 1.0.0 /absolute/path/dms
```

Повторить упаковку для каждой нужной архитектуры. В `.runtime/release/linux-ARCH`
будут DMS service binary, четыре `.dms.tar.gz` (Core и три интеграции) и
`release-set.json` с версиями, исходными коммитами, размерами и SHA256.
Это согласованный локальный комплект, не публикация в удалённый каталог.
Проверить SHA256 до передачи и после копирования. Устанавливать только архивы
из доверенного источника: исполнения чужого worker в sandbox здесь нет.

## Перенос существующего HomeNet

1. До изменений проверить актуальные адреса, архитектуру, версии nginx/mihomo,
   Account и DMS, доступ по SSH в обход панели, свободное место и отсутствие
   работающих заданий DMS/обзора LTE/установки VPN. Снять внешний backup runtime,
   init scripts, routes/applied, runtime.env, access/launcher, сертификатов,
   секретов и баз истории. Не публиковать backup или токены в журнале задачи.
2. Отдельно обновить DMS до service binary 0.4.0, сохранив `/opt/dms`, token и
   прежний binary для отката; использовать существующий init `S97dms`.
   Сам DMS не обновляется в выполняющемся им задании с немедленным restart.
3. Через DMS подготовить Core и все три пакета нужной архитектуры. Интеграции
   попадут в `/opt/share/homenet/integrations/ID/VERSION`, Core — в
   `/opt/share/homenet/core/releases/VERSION`. Staging интеграций не запускает
   процессы. Установка Core также не меняет `current` и автозапуск.
4. Выполнить предварительный план миграции и проверить указанные пути:

```sh
RELEASE=/opt/share/homenet/core/releases/1.0.0
"$RELEASE/platformctl" migrate --dry-run=true
"$RELEASE/platformctl" migrate --dry-run=false
"$RELEASE/activate-modular.sh" "$RELEASE" --dry-run
```

`migrate` сохраняет новую Core config, каталог и реестр в
`/opt/etc/homenet/core`, private backup исходных конфигураций и hashes в
`migration.json`. Рабочие данные остаются на прежних путях. Повтор с теми же
входными данными допустим; изменение источников требует нового плана, а не
перезаписи подготовленного состояния. CLI не исполняет runtime.env как shell.
Если конфигурация была изменена между подготовкой и cutover, проверка откажет.

После разрешения на переключение:

```sh
"$RELEASE/activate-modular.sh" "$RELEASE" --apply
```

Скрипт останавливает старый manager, повторно проверяет hashes источников,
сохраняет его init под скрытым именем, создаёт Core current/init и проверяет
`/health/ready`. Guard проверяет управляющие процессы и незавершённые операции,
но не заменяет проверку реального DNS, доменов, TLS, VPN и доступа Account.
При отказе новые писатели останавливаются до запуска старого manager.
nginx, mihomo, Account и DMS не останавливаются переключением интеграций.

После cutover проверить портал/ACL, основные домены, DNS/KeenDNS, VPN и историю
мониторинга, убедиться в отсутствии двух сборщиков, измерить RSS/CPU и наблюдать
доступность. ARM/MIPS runtime и живые функции требуют приёмки на устройствах.

## Пустая установка

Подготовить Account, DMS и Core. Создать private Core config с `listen`,
`state_dir`, `static_dir`, `packages_dir`, `account_url`, `dms_url`,
`dms_token_file`, `worker_app_dir`, `worker_env`, `manage_workers: true`.
Адреса Account/DMS — loopback с явным портом. Реестр может отсутствовать:
Core откроется с пустым набором. Создать `current` на подготовленный Core и
установить `S99homenet-core`; legacy manager в этот момент не должен работать.
Интеграции загружаются из каталога: проверка архива → подготовка версии →
план установки → выполнение. Установщик интеграции не устанавливает сам nginx,
роутер или VPN-конфигурацию: подключение настраивается в её существующих экранах.

## Операции из панели

- «Интеграции»: подготовить архив через DMS, выбрать версию, просмотреть план,
  установить, включить, отключить, сменить версию или удалить управление.
- «Набор версий»: выбрать действия нескольких модулей; зависимости и хеши
  проверяются для всего набора. Потребители останавливаются до зависимостей;
  запуск идёт в обратном порядке. При отказе запуска восстанавливается прежний
  набор. Семантика — восстановление по журналу, а не мгновенное переключение
  всех процессов одной машинной инструкцией.
- «История»: устойчивые операции и их ошибки, повтор восстановления. Повтор
  operation id не выполняет установку снова; устаревший план нужно пересоздать.
- «Система»: обычные приложения DMS. В модульном режиме декларации доменов
  переносятся в черновик Proxy отдельной кнопкой. После переноса проверить
  изменения и применить их в Proxy. Исходный draft сохраняется в backup.
  Перенос можно повторить; наличие декларации не означает публикацию домена.
- Недоступность DMS блокирует загрузку новых архивов, но не операции с уже
  подготовленными версиями и не чтение сохранённого портала.

Account/launcher остаются на сохранённых путях. Proxy единолично управляет
routes/applied/nginx/DNS/KeenDNS; VPN — mihomo config и своим runtime; Network —
историей связи и диагностикой. Proxy передаёт VPN DNS через приватный контракт
Core с отдельными серверными credentials. Браузерные cookies туда не подходят.
Прерывание или посторонняя правка файла блокируют дальнейшее переключение до
восстановления; чужие изменения не перезаписываются предположением об успехе.

## Восстановление

Core автоматически восстанавливает незавершённый release-set до обслуживания
операций. Файлы журнала: `STATE/operations`, `STATE/transactions`; credentials
и backup private. Не удалять журнал, чтобы «снять блокировку».
Если требуется повтор: «История → Повторить восстановление» или, при
остановленном Core, `platformctl recover --config /opt/etc/homenet/core/config.json`.
CLI защищён тем же lock и не запускает второй координатор рядом с Core.
Несовместимая схема данных или изменённые артефакты требуют отдельного решения;
обычный откат версии намеренно отклоняется.

Возврат к старому manager при первой миграции:

```sh
"$RELEASE/activate-modular.sh" "$RELEASE" --rollback
```

Останавливаются Core/workers, затем восстанавливается старый автозапуск.
Используются текущие совместимые файлы данных, новые записи истории и ACL не
затираются старым backup. Если процесс ещё завершает LTE/config job, скрипт
отказывается запускать второго писателя; дождаться завершения и повторить.
Для нестандартного Core current задать `HOMENET_CORE_CURRENT` также службе DMS,
чтобы она корректно определяла владельца маршрутов.

Перед будущим обновлением самого Core остановить его через init, сохранив
старые release/current и config. Переключать Core только после staging и
проверки совместимости API всех установленных интеграций; после readiness
проверить доступ, при отказе вернуть прежний Core. UI смены версий относится
к интеграциям, а не к замене самой базовой службы Core.

## Локальные проверки

В `backend`: `go test ./...`, `go test -tags integration_worker ./manager`,
`go test -race ./internal/core ./internal/integration ./manager`, `go vet ./...`.
В DMS: `go test ./...`, `go vet ./...`. Тесты shell lifecycle запускать в Linux/WSL.
Сборщик проверяет TypeScript и собирает Core UI + три ES-пакета.

`node scripts/modular-preview.mjs proxy,network,vpn` запускает настоящий Core
с Account/worker stubs на loopback. `node scripts/modular-preview.mjs none 48661`
показывает пустую установку. Управляющие действия в этой UI-фикстуре отключены;
операции/rollback/перезапуск проверяются Go-тестами отдельно. Никаких реальных
устройств фикстура не опрашивает. Не выставлять её на внешний интерфейс.
