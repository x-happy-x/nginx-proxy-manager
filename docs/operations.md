# Эксплуатация HomeNet на Keenetic

Этот документ относится к отдельному прокси HomeNet. Исходники собираются на Windows, рабочие процессы остаются на роутере. Текущий менеджер доступен по `http://192.168.1.1:63412/`, SSH — `192.168.1.1:222`. Пароли в репозитории не хранятся.

## Что принадлежит HomeNet

- Приложение, маршруты, UI, runtime: `/opt/etc/homenet/nginx/`.
- Отдельный nginx: `/opt/etc/homenet/proxy/nginx.conf`, `/opt/etc/homenet/proxy/nginx.pid` и вложенные управляемые конфиги.
- Логи прокси: `/opt/var/log/homenet/`; лог менеджера: `/opt/var/log/nginx-manager-lite.log`.
- Init-скрипты: `S20-nginx-ips`, `S98nginx-local-conf`, `S99nginx-manager-lite`.
- Последняя успешно применённая схема: `/opt/etc/homenet/nginx/.runtime/applied.yml`; путь переопределяется `APPLIED_ROUTES_PATH`.
- Собственный блок `# BEGIN HOMENET MANAGED HOSTS` / `# END HOMENET MANAGED HOSTS` в системном hosts. На этом роутере `/etc/hosts` разрешается в `/tmp/hosts`.

Штатная конфигурация `/tmp/nginx/nginx.conf` читается для повторного использования сертификата Keenetic. HomeNet не должен редактировать этот файл или перезапускать штатный nginx.

## Проверенная установка 22 сентября 2026

Sublab открывается до страницы входа по локальному HTTP и публичному HTTPS с доверенным сертификатом. Пользователь подтвердил публичный вход через мобильный интернет с выключенным Wi‑Fi; соответствующий трафик зарегистрирован на порту 24192 как внешний. DNS `sub.local`, `sub.crubs.crazedns.ru` и `account.local` внутри сети возвращает `192.168.1.2`. Штатный nginx и Mihomo сохранили исходные PID, проверка интернета после переключения прошла.

Это не подтверждение работоспособности всех прежних приложений: при прямой проверке старых upstream не ответили Plane, Proxmox s2, Vless, LMS и Netping. Их конфигурация сохранена. HTTPS Proxmox s1 использует локальную цепочку сертификатов; проверка стандартным доверенным хранилищем клиента её не приняла.

## Перед изменениями

Рабочие маршруты и файл черновика могут различаться: после **Сохранить черновик** работающий nginx продолжает обслуживать ранее применённые маршруты. При резервном копировании сохраняйте и `routes.yml`, и `.runtime/applied.yml`, и текущий каталог отдельного прокси.

Сохраните отдельную копию соответствующего релиза: бинарников, UI, `runtime.env`, трёх init-скриптов, обоих YAML-файлов, каталога `/opt/etc/homenet/proxy`. Для изменений DNS/KeenDNS также сохраните текущие затрагиваемые записи. Локальные копии размещайте внутри `.local/` на Windows. Исходная копия роутера до переделки находится в `.local/router-backup-20260921/`.

Исходная копия содержит прежнюю схему с общими nginx-файлами. Это материал для точечного восстановления, а не готовый каталог для слепой замены новой изолированной установки. Резервные копии могут содержать ключи сертификатов и частные настройки.

## Проверка без переключения прокси

Из Windows:

```powershell
Invoke-RestMethod http://192.168.1.1:63412/api/nginx/status
Invoke-RestMethod http://192.168.1.1:63412/api/ndns/http
Invoke-RestMethod 'http://192.168.1.1:63412/api/nginx/stats?window=1h'
```

Статус должен относиться к отдельному master-процессу HomeNet и его конфигурации. «Работает» не является health-check каждого приложения.

На роутере:

```sh
/opt/etc/init.d/S98nginx-local-conf status
/usr/sbin/nginx -p /opt/etc/homenet/proxy/ -c /opt/etc/homenet/proxy/nginx.conf -t
tail -n 60 /opt/var/log/homenet/error.log
tail -n 60 /opt/var/log/nginx-manager-lite.log
```

Кнопка **Применить → Проверить конфигурацию** вызывает `POST /api/apply/check`. Она проверяет схему, свободные новые listeners, совместимость локальных DNS-записей, условия KeenDNS/Mihomo и выполняет dry-run генератора. Проверка новых портов кратко открывает и закрывает только ещё не занятые сокеты; работающие listeners не останавливаются.

CLI-предпросмотр генератора:

```sh
cd /opt/etc/homenet/nginx
bin/linux-arm64/nginx --config routes.yml --dry-run
```

`dry_run: true` и `nginx_validated: false` означают предпросмотр. Эта команда сама не заменяет проверку `nginx -t` и не синхронизирует роутер. Не публикуйте полный вывод конфигов: в окружении могут присутствовать чувствительные сведения.

## Обычное применение маршрутов

Пользуйтесь мастером **Сервисы**, сохраните черновик, выполните проверку и явное применение. Сначала генератор подготавливает конфиги в отдельном каталоге и проверяет их штатным бинарником. Затем обновляется только выделенный экземпляр nginx; DNS и KeenDNS синхронизируются после подготовки прокси. Результат операции содержит выполненные шаги и ошибки.

При ошибке система пытается восстановить прежние управляемые файлы и затронутые записи. Ошибка отката явно сообщается. Не воспринимайте сетевую ошибку браузера или незавершённый ответ как доказательство успешного применения либо полного отката: сначала проверьте состояние через API и логи.

Прямой вызов генератора или CLI `homenet apply` относится к генерации nginx и не заменяет полный workflow менеджера с DNS, KeenDNS и сохранением последней применённой схемы.

## Как проверять Sublab

Рабочий маршрут: приложение `192.168.99.20:4192`, локальное имя `sub.local`, публичное `sub.crubs.crazedns.ru`, IP прокси `192.168.1.2`, отдельный внешний порт `24192`. Если порт выбран автоматически, используйте фактическое значение сохранённого маршрута. Для входа Sublab также настроен `account.local` → `192.168.99.20:4161`; публичный вход использует существующий `account.crubs.crazedns.ru`.

С Windows, сначала upstream:

```powershell
curl.exe --max-time 10 -s -o NUL -w '%{http_code}' http://192.168.99.20:4192/
Resolve-DnsName sub.local -Server 192.168.1.1
Resolve-DnsName sub.crubs.crazedns.ru -Server 192.168.1.1
curl.exe --max-time 10 -s -o NUL -w '%{http_code}' http://sub.local/
curl.exe --max-time 10 -s -o NUL -w '%{http_code}' https://sub.crubs.crazedns.ru/
```

Оба DNS-имени должны разрешаться в локальный адрес прокси. Для проверки самого nginx независимо от кеша DNS:

```powershell
curl.exe --max-time 10 -s -o NUL -w '%{http_code}' --resolve sub.local:80:192.168.1.2 http://sub.local/
curl.exe --max-time 10 -s -o NUL -w '%{http_code}' --resolve sub.crubs.crazedns.ru:443:192.168.1.2 https://sub.crubs.crazedns.ru/
curl.exe --max-time 10 -s -o NUL -w '%{http_code}' -H 'Host: sub.crubs.crazedns.ru' http://192.168.1.2:24192/
```

Не добавляйте `-k` к обычной HTTPS-проверке: без проверки цепочки тест не подтверждает доверенный сертификат. Для Sublab ожидается 302 на авторизацию; его HEAD отвечает иначе, поэтому примеры используют GET.

Последний запрос проходит через выделенный внешний вход, но сделан из LAN. Проверка реального WAN выполняется отдельно: открыть публичный HTTPS с другого интернет-подключения, затем сопоставить запрос со временем и источником в журнале. Нельзя объявлять WAN проверенным только по `--resolve` или прямому обращению к выделенному порту.

## DNS и Mihomo

В `runtime.env` установлен режим `MIHOMO_DNS_MODE=system-hosts`. Менеджер читает конфиг Mihomo и проверяет, что системные hosts разрешены. Явно отключённые `dns.use-hosts` или `dns.use-system-hosts`, а также конфликтующий YAML-host приводят к отказу до изменения настроек.

Изменяется только помеченный блок в hosts. Прочие строки сохраняются, перед записью создаётся приватная копия `.homenet-hosts-backup-*` рядом с фактическим файлом. Mihomo не перезапускается, YAML и активный профиль не переключаются. Проверка на текущем роутере подтвердила подхват hosts без смены PID Mihomo; внутреннее обновление занимает до пяти секунд, DNS TTL и клиентские кеши могут добавить задержку.

Раз в минуту менеджер восстанавливает hosts-блок из **применённой**, а не сохранённой схемы, если выделенный прокси проходит проверку работоспособности. Если `/tmp/hosts` был пересоздан системным компонентом, ручное переключение профиля Mihomo не требуется.

Записи `ndmc ip host` добавляются только при отсутствии подходящей записи. Если имя уже связано с другим IP, менеджер не затирает его молча. Оператор должен проверить конфликт и исправить конкретную запись через **DNS и KeenDNS**. Чужие DNS-записи и proxy-профили не удаляются общей очисткой.

## Сертификаты публичного домена

Политика хоста `tls.cert_policy: keenetic` использует подходящую пару сертификата и зашифрованного ключа из действующей конфигурации Keenetic. Ключ остаётся в формате, который понимает `/usr/sbin/nginx`; обычный Entware nginx может не поддерживать его. HomeNet создаёт собственные закрытые карты сертификатов, не изменяя nginx роутера.

Если сертификат отсутствует, истёк, не подходит имени или не поддерживается выбранным бинарником, устраните причину по диагностике проверки. Не меняйте глобальный nginx и не отключайте проверку TLS в клиенте для маскировки ошибки.

## Перезапуск только своего компонента

Для перечитывания отдельного nginx после успешной проверки:

```sh
/opt/etc/init.d/S98nginx-local-conf reload
```

Для обновления менеджера без перезапуска прокси:

```sh
/opt/etc/init.d/S99nginx-manager-lite restart
```

`S98` проверяет путь конфигурации, директиву PID и командную строку процесса перед отправкой HUP. `restart` в этом скрипте также выполняет graceful reload, если его master уже работает.

Не используйте для этой задачи общий `nginx -s reload` без явной отдельной конфигурации, `killall nginx`, перезапуск сетевых интерфейсов, рестарт Mihomo или восстановление полного `running-config`. Не удаляйте IP-aliases, пока ими пользуются активные сервисы.

## Обновление и откат

Сначала выполните `scripts/build-windows.ps1` на Windows. Сборка не развёртывает результат. Перенос должен быть адресным: новый комплект бинарников и UI подготавливается отдельно, проверяется, а предыдущий комплект сохраняется до завершения проверки. Перед обновлением используйте конкретный проверенный путь резервного релиза; не угадывайте его по имени.

Скрипт адресного развёртывания — `scripts/deploy-router.py` (Python 3, пакеты `paramiko` и `PyYAML`). С `--key` он входит по SSH-ключу, например `--key ~/.ssh/keenetic_ed25519`; без него запрашивает пароль интерактивно либо читает `ROUTER_PASSWORD`. Пароль не следует помещать в командную строку или файлы проекта.

```powershell
python scripts/deploy-router.py --routes routes.yml
```

Свежий экспорт рабочих маршрутов (на роутере нет `sftp-server`, поэтому `scp` не работает):

```powershell
cmd /c "ssh keenetic cat /opt/etc/homenet/nginx/routes.yml > .local\routes-live.yml"
python scripts/deploy-router.py --routes .local/routes-live.yml --key ~/.ssh/keenetic_ed25519
```

Без `--activate` создаётся резервный комплект и тестовый менеджер на порту `63414`, затем запускается предварительная проверка. Это не полностью пассивный dry-run: на роутер копируются файлы и запускается тестовый процесс; при отсутствии отдельного прокси скрипт подготавливает его. Публичные записи ещё не переключаются. Используйте свежий экспорт рабочих маршрутов для последующих обновлений, чтобы не заменить более новую конфигурацию старым файлом из проекта.

Активация выполняется отдельным запуском:

```powershell
python scripts/deploy-router.py --routes routes.yml --activate
```

Комплекты хранятся в `/opt/etc/homenet/releases/<дата-время>/`, предыдущие файлы — в `before/`. Перед переключением создаётся удалённый watchdog: без маркера `COMMITTED` он запускает `rollback.sh` через 180 секунд. Маркер устанавливается после проверки рабочего менеджера и отдельного прокси. Результат успешной активации и путь сценария отката сохраняются на Windows в `.local/last-deployment.json`. Наличие скрипта не является результатом проверки конкретного обновления: изучите фактический вывод, preflight/apply-файлы и состояние после запуска.

Подготовленный `rollback.sh` предназначен для немедленного возврата именно этого обновления. Для позднего отката после новых изменений сначала сравните резервную копию с текущим состоянием, чтобы не потерять новые маршруты и DNS-записи. Не удаляйте сохранённый релиз до окончания проверки.

Если обновлён только UI/менеджер, восстановите их из выбранного предыдущего комплекта и перезапустите только `S99nginx-manager-lite`. Не заменяйте `routes.yml` старой копией автоматически: в нём могут быть более новые черновики пользователя.

Если требуется вернуть маршруты, сохраните текущий черновик, загрузите проверенную прежнюю применённую схему, выполните проверку и примените её через менеджер. Для отказавшего отдельного nginx восстанавливайте только его собственные конфиги, проверьте явной командой `nginx -p ... -c ... -t`, затем выполните `S98nginx-local-conf reload` или `start`.

Для DNS/KeenDNS восстанавливайте только конкретные записи, затронутые этим изменением, с учётом их сохранённых предыдущих значений. Для hosts-блока используйте последнюю применённую схему или содержимое его приватной копии, сохраняя новые чужие строки. Не подменяйте целиком конфигурацию роутера или весь `/tmp/hosts` резервной копией без сравнения.

Если восстановление невозможно подтвердить или процесс из PID-файла не совпадает с выделенным master, остановитесь на диагностике: скрипты намеренно отказываются сигнализировать чужому процессу.

## Накопительная статистика

Менеджер раз в минуту проверяет три явно заданных файла `route_access.log`, `access.log`, `error.log`. Файл свыше `PROXY_LOG_MAX_MB` (по умолчанию 16 МиБ) переименовывается с сохранением четырёх предыдущих файлов `.1`–`.4`. После проверки PID и командной строки только выделенному nginx отправляется `USR1`, чтобы открыть новые журналы без остановки запросов. Порог не является жёсткой квотой: между проверками файл может вырасти больше него. Сырые логи за пределами четырёх архивов удаляются; накопленные агрегаты сохраняются отдельно.

По умолчанию состояние находится в `/opt/var/log/homenet/route_access.log.stats.gz`; переопределение — `STATS_STATE_PATH`. Обновление состояния идёт атомарно через временный файл, раз в 60 секунд. Чтение журнала продолжается каждые две секунды, максимум 4 МиБ за цикл; память и число минутных агрегатов ограничены. Это не бессрочная аналитическая база: горизонт запросов — 1, 6 или 24 часа.

При диагностике `GET /api/nginx/stats` учитывайте `sample.coverage_from`, `backlog_bytes`, `gaps`, `persisted` и `persistence_error`. `truncated` означает неполное покрытие периода, а не обязательно обрезанный хвост текущего файла. `resolution_seconds: 60` задаёт разрешение агрегатов. p95 отмечен как приблизительный; средние и счётчики относятся к фактически прочитанным запросам.

Ротация и copytruncate сохраняют накопленные корзины. При недоступном старом хвосте лога фиксируется gap. Состояние не содержит тела HTTP-запросов, но имена доменов и статистика остаются частными данными. Для переноса статистики сохраните её gzip-файл вместе с соответствующими логами, не смешивая состояние разных установок.

## Локальный стенд на Windows

Всегда используйте копию маршрутов и отдельные каталоги. Пример из корня проекта:

```powershell
$previewRoot = Join-Path (Get-Location) '.local/preview'
New-Item -ItemType Directory -Force -Path $previewRoot | Out-Null
Copy-Item .\routes.yml (Join-Path $previewRoot 'routes.yml')
$env:CONFIG_ENV_PATH = Join-Path $previewRoot 'missing.env'
$env:ROUTES_PATH = Join-Path $previewRoot 'routes.yml'
$env:NGINX_CONF_ROOT = Join-Path $previewRoot 'nginx'
$env:ROUTE_ACCESS_LOG = Join-Path $previewRoot 'route_access.log'
$env:STATIC_ROOT = Join-Path (Get-Location) 'frontend/static'
$env:LITE_UI_HOST = '127.0.0.1'
$env:LITE_UI_PORT = '18490'
.\bin\windows-amd64\manager.exe
```

Открыть `http://127.0.0.1:18490/`. На Windows `ndmc` и роутерный nginx отсутствуют: ошибки соответствующих диагностических разделов ожидаемы. Добавление сервиса и сохранение записывают только локальную копию. Этот стенд не заменяет проверку выделенного nginx на роутере. Завершайте процесс стенда в том же терминале после проверки.
