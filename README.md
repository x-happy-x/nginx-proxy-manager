# HomeNet Proxy Manager

## Развёртывания через DMS

Страница «Развёртывания» подключается к DMS API: показывает приложения, версии,
иконки, релизы и журнал операций; принимает готовый архив с компьютера или HTTPS
URL вместе с SHA256. Кнопка «Проверить пакет» выполняет dry-run. Установка и
восстановление релиза запускаются отдельно в DMS и продолжаются при перезапуске
менеджера. После завершения обновите список приложений кнопкой «Обновить».

Настройки менеджера: `DMS_API_URL=http://127.0.0.1:63416`,
`DMS_TOKEN_FILE=/opt/dms/token`. Токен читает backend; браузер его не получает.
Доступ к операциям проходит через обычную проверку администратора HomeNet и
проверку origin. Пока API не установлен, остаётся просмотр старых файлов метаданных.

В DMS v0.3.0 сначала установите бинарник службы, затем на роутере выполните
`/opt/bin/dms-service install-api` и `/opt/etc/init.d/S97dms start`.
Это отдельный сервис; порт 63415 остаётся у шлюза Account.

Для выпуска HomeNet: `dms-client pack --config dms.yml --output homenet.dms.tar.gz`
или `pack --skip-build` после готовой сборки. `dms-client apply --config dms.yml
--api <DMS URL>` собирает и отправляет пакет через API. На клиенте требуется
`DMS_API_TOKEN`; для удалённого подключения используйте HTTPS.

Манифест HomeNet обновляет только runtime: бинарники, React-интерфейс и init
менеджера. Он сохраняет `routes.yml`, `.runtime/applied.yml`, `config/runtime.env`,
параметры Account, сертификаты и данные; устаревшие `.local` маршруты не создаются.

HomeNet связывает домены с локальными HTTP-сервисами и настраивает их доступ через Keenetic. Исходники и сборка находятся на Windows в `P:\services\nginx-proxy-manager`; менеджер и отдельный экземпляр nginx работают на роутере.

Интерфейс: **http://192.168.1.1:63412/**. Это административный интерфейс локальной сети; публичный домен нужен приложению, а не менеджеру.

## Как проходит запрос

Для сервиса Sublab `192.168.99.20:4192`:

- `http://sub.local` внутри сети → `192.168.1.2:80` → Sublab.
- `https://sub.crubs.crazedns.ru` внутри сети → `192.168.1.2:443` → Sublab.
- Публичный HTTPS из интернета → KeenDNS → отдельный вход HomeNet, например `192.168.1.2:24192` → Sublab.

DNS обоих имён внутри сети указывает на IP прокси. Раздельные входные порты позволяют учитывать локальные и внешние запросы отдельно. Метка источника означает входной маршрут: прямое тестовое обращение к порту KeenDNS тоже учитывается как внешнее.

## Добавить сервис

1. Открыть **Сервисы → Добавить сервис**.
2. Указать название, адрес приложения, порт и протокол его upstream.
3. Указать локальный домен и, при необходимости, поддомен публичной зоны. Суффикс `.crubs.crazedns.ru` закреплён в мастере: вводится только одна метка, например `sub`, а итоговое имя будет `sub.crubs.crazedns.ru`. Затем указать локальный IP прокси. Для внешнего входа можно оставить `auto_random`; назначенный порт сохраняется в конфигурации.
4. Нажать **Добавить в черновик**, затем **Сохранить черновик**.
5. Открыть **Применить → Проверить конфигурацию**, изучить результат и нажать **Применить на роутере**.

**Сохранение черновика записывает `routes.yml`, но не меняет работающий прокси, DNS или KeenDNS.** Проверка проверяет схему, предварительные условия интеграций и рендер конфигурации. Это dry-run: вывод `nginx_validated: false` ожидаем. Настоящая проверка подготовленного конфига командой `nginx -t` выполняется при применении до переключения прокси.

Новый локальный домен по умолчанию использует HTTP. Новый публичный домен внутри сети использует HTTPS с политикой `keenetic`; сертификат берётся из действующей конфигурации Keenetic. Для публичного имени нужен домен, обслуживаемый KeenDNS этого роутера, и подходящий действующий сертификат. Произвольный чужой домен не создаётся автоматически.

`.local` поддерживается как запрошенное имя, но на части клиентов этот суффикс обрабатывает mDNS. Если клиент игнорирует обычный DNS, используйте `.home.arpa` или настройте разрешение имён на самом клиенте.

## Интерфейс

Интерфейс рассчитан на экраны от 320 px. На широком экране разделы сгруппированы в боковом меню: рабочее пространство, сеть и безопасность, система. При ширине меньше 1024 px меню выдвигается кнопкой в верхней панели, таблицы на телефоне превращаются в карточки, диалоги открываются снизу. Тема переключается кнопкой с луной или солнцем; выбор сохраняется в браузере, при первом открытии используется системная тема.

В верхней панели всегда видны состояние прокси, **центр операций** (результаты проверок, сохранений и ошибки текущего сеанса) и кнопка **Применить**.

Несохранённые правки показывает плавающая панель внизу экрана, а разделы с правками отмечены точкой в меню:

- **Черновик маршрутов изменён** — «Сохранить черновик» записывает `routes.yml` (или Ctrl+S), «Отменить» возвращает последнее сохранённое состояние.
- **DNS / KeenDNS изменены** — «Записать на роутер» сразу меняет записи роутера, «Отменить» возвращает прочитанное с роутера.

**Применить** открывает пошаговый диалог: сохранить черновик → проверить конфигурацию → применить на роутере. Каждый шаг показывает вывод менеджера; применить можно только после успешной проверки сохранённого файла.

- **Обзор:** фильтры периода (1/6/24 часа), домена и источника действуют на все показатели. Запросы, доля успешных ответов, p95 и средняя задержка, объём ответов; график с подсказкой по наведению и табличным видом; источники трафика, коды ответов, нагрузка по доменам. Обновление каждые 30 секунд при открытой вкладке.
- **Сервисы:** поиск по имени, адресу и домену, фильтр «локальные / с внешним доступом», ссылки на домены, мастер приложения и его доменов.
- **Журнал запросов:** новые записи сверху; фильтр, статусы, источник; панель с разобранной записью (клиент, вход, тайминги upstream, размеры, User-Agent) и исходным JSON; экспорт JSONL.
- **Маршрутизация:** вкладки приложений, хостов и слушателей: TLS, перенаправление, SAN, локальный DNS, вход KeenDNS, порты, заглушка и адрес интерфейса.
- **DNS и KeenDNS:** добавление, поиск и фильтр DNS-записей по типу, редактирование адресов, публичные входы KeenDNS.
- **Сертификаты:** политика TLS, состояние локального CA, выпуск сертификатов для маршрутов, проверка и скачивание CRT/KEY, удаление с подтверждением.
- **Система**, **Логи nginx**, **Развёртывания:** процесс nginx, файл маршрутов, конфигурационные файлы, журналы с подсветкой ошибок, релизы DMS. Секретные карты сертификатов и приватные ключи не выдаются редактором nginx-конфигов.

Изменение приложения через простой мастер сохраняет дополнительные домены, существующие политики TLS и параметры доступа KeenDNS. Удаление приложения удаляет его связанные маршруты из черновика. При применении удаляются только DNS-пары и публичные записи, принадлежавшие последней применённой конфигурации; при несовпадении с текущим состоянием роутера операция останавливается до изменений. Посторонние записи сохраняются. Конфликт с существующим DNS-адресом требует явного решения оператора.

## Прокси mihomo

Группа меню «Прокси mihomo» заменяет отдельную панель zashboard. Браузер обращается только к менеджеру: `/api/mihomo/*` пересылается в контроллер mihomo по белому списку путей, секрет контроллера подставляет менеджер и в браузер не попадает. Запрещены `PUT /configs` с путём или содержимым, смена `external-controller`/`secret`/`external-ui`, загрузка UI и хранилище zashboard. WebSocket и изменяющие запросы принимаются только с того же origin.

- **Прокси и группы:** выбор узла, снятие закрепления, проверка задержки узла и группы, сортировка, подписки с трафиком и сроком, обновление и проверка узлов.
- **Проверка подписок:** адаптивная проверка форка `x-happy-x/mihomo` — режим сети (без ограничений / белые списки / нет сети), прямые контрольные адреса, рейтинги для обычной сети и белых списков, этап, на котором проба не прошла, статусы с учётом `failure-threshold`/`recovery-threshold`.
- **Соединения:** живой поток, закрытые за сеанс, сводка по устройствам, имена устройств из Keenetic (`/show/ip/hotspot`), закрытие одного или всех, переход в «Анализатор».
- **Правила:** счётчики срабатываний, выключение на лету, наборы правил.
- **Трафик**, **Журнал ядра:** скорость, память, выходы, устройства; поток журнала по уровню, экспорт JSONL.
- **Конфигурация:** подписки (в том числе адаптивная проверка с `timeout`, `content-type`, `body-regex`, `body-not-regex` и порогами), шаблон «Проверка сервиса» для ChatGPT/Claude/Gemini с каскадом `depends-on` от базовой подписки (MIHOMO-6: узлы, не прошедшие базу, помечаются «ждёт базу» и сервис их не проверяет), правила, группы, свои узлы (включая OLCRTC), устройства (своё имя и маршрут устройства через `SRC-IP-CIDR`), DNS и TUN, YAML целиком. Правки копятся в черновике; «Проверить и применить» прогоняет `mihomo -t`, сохраняет `.homenet-backup-*.yaml` рядом с конфигом, заменяет `config.yaml` и перечитывает его через контроллер; при ошибке файл и состояние ядра возвращаются. `secret` и адрес контроллера не меняются даже из YAML-редактора.
- **Система → Ядро mihomo:** режим, TUN и стек, allow-lan, IPv6, уровень журнала, DNS-запрос, сброс DNS и fake-ip, перечитать конфиг, гео-базы, обновление и перезапуск ядра с подтверждением. Режим ядра и скорость видны в верхней панели.

Если mihomo не найден, страницы группы показывают мастер установки: последний релиз `x-happy-x/mihomo` для процессора роутера, сверка с `sha256sums.txt`, проверка `mihomo -v`, стартовый `config.yaml` (controller `127.0.0.1:9090`, новый secret, первая подписка), `mihomo -t`, служба `/opt/etc/init.d/S24mihomo`. Установщик XKeen задаёт вопросы, поэтому при выборе XKeen мастер выдаёт команду для SSH. Мастер запускается только кнопкой «Установить».

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `MIHOMO_CONTROLLER` | `http://127.0.0.1:9090` | контроллер; только loopback |
| `MIHOMO_SECRET` | из `secret:` конфига | секрет контроллера |
| `MIHOMO_CONFIG` | `/opt/etc/mihomo/config.yaml` | редактируемый конфиг |
| `MIHOMO_BINARY` | первый из `/opt/sbin/mihomo`, `/opt/bin/mihomo` | для `mihomo -t` и установки |
| `MIHOMO_HOME` | каталог конфига | каталог `-d` для проверки |
| `MIHOMO_STATE_DIR` | `/opt/etc/homenet/mihomo` | свои имена устройств |
| `MIHOMO_RELEASE_BASE` | `https://github.com/x-happy-x/mihomo/releases/latest/download` | источник релизов для мастера (зеркало) |

## Страница «Сервис недоступен»

Если выделенный nginx не может достучаться до приложения, вместо стандартной страницы nginx открывается страница HomeNet с кодом ответа, цепочкой «Вы → Прокси → приложение», временем запроса, кнопкой «Повторить» и автоповтором (15 секунд, затем реже, до 2 минут; повтор можно выключить).

- **502** — приложение не приняло подключение: остановлено, слушает другой порт или компьютер выключен.
- **504** — приложение не ответило вовремя: компьютер недоступен по сети или приложение зависло.

На локальных входах страница показывает адрес приложения, список того, что проверить, и ссылку на менеджер. На внешнем входе KeenDNS внутренние адреса и подсказки не показываются. Собственные ответы приложения, включая его 502/503, передаются без изменений.

Страницы генерируются вместе с конфигурацией при применении: `NGINX_CONF_ROOT/errors/<домен>.<local|public>.<код>.html`. Штатный nginx роутера собран без SSI, поэтому для каждого домена и кода создаётся отдельный файл, а время, путь и отсчёт добавляет встроенный скрипт.

## Изоляция от основного трафика роутера

HomeNet запускает **отдельный master-процесс** штатным бинарником `/usr/sbin/nginx`, с конфигурацией и PID внутри `/opt/etc/homenet/proxy`. Использование штатного бинарника необходимо, в частности, для сертификатов Keenetic с зашифрованным ключом; ключи не расшифровываются и не выводятся в UI.

- `S20-nginx-ips` добавляет только явно разрешённые aliases `br0=192.168.1.2/24` и `br2=192.168.99.2/24`. Он не выводит интерфейсы из строя, не вычисляет новые адреса и не перезапускает сеть.
- Прошивка Keenetic пропускает TLS на порт 443 адресов роутера только с SNI его собственных доменов (цепочка `_NDM_HTTP_INPUT_TLS_` в `mangle`), остальное молча отбрасывает — поэтому, например, `https://xkeen.local` на алиасе зависал бы на рукопожатии. Хук `/opt/etc/ndm/netfilter.d/60-homenet-tls-sni.sh` (исходник — `netfilter.d/`) ставит в `mangle INPUT` одно правило `ACCEPT` на порт 443 только для этих двух алиасов; веб-интерфейс роутера на его собственных адресах остаётся под фильтром. ndm применяет хук после каждой перестройки netfilter, `S20-nginx-ips` — при загрузке; `… remove` снимает правила.
- `S98nginx-local-conf` проверяет отдельную конфигурацию, PID и командную строку master-процесса. Reload направляется только этому процессу. Штатный nginx Keenetic не перезапускается.
- `S99nginx-manager-lite` управляет только менеджером.
- Применение не требует перезапуска Mihomo, изменения маршрутов, firewall (кроме описанного исключения TLS для алиасов), режима DNS или активного профиля VPN.

В текущей конфигурации используется `MIHOMO_DNS_MODE=system-hosts`. Менеджер меняет только свой помеченный блок в системном hosts-файле; `/opt/etc/mihomo/config.yaml` читается для проверки, а не переписывается. Другие записи сохраняются. При работающем системном DNS Mihomo подхватывает hosts без reload; учитывайте его короткий кеш и кеш клиента. Менеджер также восстанавливает блок по последней успешно применённой конфигурации, если системный hosts был пересоздан.

## Пути и конфигурация

Источник маршрутов — схема v2.1 в `routes.yml`: `apps` описывает upstream, `hosts` связывает домен с `app_id`, `endpoints` задаёт локальный и выделенный KeenDNS-входы. Порты должны быть уникальными там, где выделен отдельный вход. Детали базовой схемы: [docs/schema-v2.1.md](docs/schema-v2.1.md).

Основные значения `config/runtime.env`:

```dotenv
ROUTES_PATH=/opt/etc/homenet/nginx/routes.yml
NGINX_CONF_ROOT=/opt/etc/homenet/proxy
NGINX_BINARY=/usr/sbin/nginx
NGINX_MAIN_CONF=/opt/etc/homenet/proxy/nginx.conf
NGINX_PID=/opt/etc/homenet/proxy/nginx.pid
NGINX_LISTEN_IPS=192.168.1.2,192.168.99.2
LITE_UI_HOST=192.168.1.1
LITE_UI_PORT=63412
ROUTE_ACCESS_LOG=/opt/var/log/homenet/route_access.log
MIHOMO_DNS_MODE=system-hosts
MIHOMO_CONFIG=/opt/etc/mihomo/config.yaml
MIHOMO_HOSTS_PATH=/etc/hosts
```

`CONFIG_ENV_PATH` позволяет выбрать другой файл окружения. Не переносите настройки рабочего роутера в локальный стенд без переопределения путей и bind-адреса.

## Сборка на Windows

Нужны Go 1.22.2 или новее, Node.js 20.19+ / 22.12+ и npm. Из корня проекта:

```powershell
.\scripts\build-windows.ps1
```

Скрипт запускает Go-тесты, собирает `manager`, генератор `nginx` и CLI `homenet` для Linux arm64 и Windows amd64, затем выполняет `npm ci` и production-сборку UI. Для сборки только Go: `-SkipFrontend`.

Результаты: `bin/linux-arm64/`, `bin/windows-amd64/`, `frontend/static/react/`. Внешний локальный `ui-kit` больше не требуется. Браузеру не нужны CDN, внешние шрифты или онлайн-сервисы для интерфейса.

Для отдельных проверок:

```powershell
Set-Location backend
go test ./...
Set-Location ../frontend
npm.cmd ci
npm.cmd run build
npm.cmd audit
```

Для работы над интерфейсом запустите менеджер локально (`bin/windows-amd64/manager.exe` с `ROUTES_PATH`, `LITE_UI_HOST=127.0.0.1`, `LITE_UI_PORT=18490` и несуществующим `CONFIG_ENV_PATH`, чтобы не подхватить пути роутера) и `npm.cmd run dev` в `frontend`: Vite проксирует `/api` на `http://127.0.0.1:18490`, другой адрес задаётся переменной `HOMENET_API`. Интерфейс откроется по адресу `http://localhost:5173/static/react/`.

Сборка сама ничего не развёртывает на роутере. Адресное развёртывание выполняет `scripts/deploy-router.py` с предварительным staging и отдельным флагом `--activate`; пароль вводится интерактивно. Обновление и диагностика описаны в [docs/operations.md](docs/operations.md). Legacy `scripts/setup.sh` выполняет установку/обновление из Git и не является безопасным способом адресного обновления уже настроенного роутера.

## Логи, статистика и ограничения проверки

Сырые access/error-логи и структурированный `route_access.log` находятся в `/opt/var/log/homenet/`. Статистика использует реальные записи запросов, не проверяет доступность приложения по искусственным запросам и не подменяет отсутствие данных нулями успешного трафика. Число сервисов означает число настроенных приложений, а не результат health-check каждого upstream.

Логи ротируются при превышении 16 МиБ (`PROXY_LOG_MAX_MB`); сохраняются четыре предыдущих файла. Проверка выполняется раз в минуту, переоткрытие журналов затрагивает только выделенный nginx и не прерывает запросы.

Накопительная статистика сохраняется отдельно от сырого журнала: `STATS_STATE_PATH`, по умолчанию `ROUTE_ACCESS_LOG + ".stats.gz"`. Сбор выполняется каждые две секунды; сжатое состояние атомарно сохраняется раз в минуту. Удерживаются минутные агрегаты до 24 часов с запасом в одну минуту, с группировкой по домену и источнику.

Счётчики учитывают прочитанные записи точно; p95 — приближённая верхняя граница интервала гистограммы из 32 корзин. Ротация сырого лога не обнуляет накопленные счётчики. Пропуски, очередь непрочитанных данных, ограничение количества агрегатов и ошибки сохранения отражаются в `stats.sample`; неполное покрытие периода нельзя интерпретировать как отсутствие трафика. Период до начала сбора восстановить нельзя. После аварийной остановки возможен промежуток после последнего сохранённого состояния; потерянные исходные записи нельзя восстановить из агрегатов.

Локальный тест через выделенный вход подтверждает маршрутизацию KeenDNS → HomeNet, но не доказывает доступность с WAN. Для полной проверки публичного домена нужен запрос из независимой внешней сети, например с телефона с выключенным Wi-Fi.

Локальные резервные копии и результаты диагностики находятся в `.local/` и исключены из Git. В резервной копии могут быть приватные ключи и конфигурация сети; её нельзя публиковать вместе с исходниками.
